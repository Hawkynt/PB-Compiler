## What it is

Zero-initialized data — variable slots, tables, buffers — does not need to be
*written* into the executable as thousands of zero bytes. It moves behind the
image: the MZ header's `MinAlloc` reserves the space, and the entry stub zeroes
it. Costless on disk, identical in memory.

This is the classic `.BSS` split, applied to a format that has no section table:
the MZ loader gives the program whatever `MinAlloc` asks for beyond the image,
already accounted for in the allocation.

## Sample

```basic
DIM buffer%(0 TO 4999)     ' 10 000 zero bytes
DIM flags%(0 TO 999)       ' 2 000 more
PRINT "ready"
```

## Without the optimizer

```
code : 12153 bytes
data :  4201 bytes
bss  :     0 bytes
```

The 12 000 zero bytes are written into the `.EXE` file, and the loader reads
them from disk on every run.

## With the optimizer

```
code :   612 bytes
data :    24 bytes
bss  : 12000 bytes
```

The file shrinks by 12 000 bytes; the program sees exactly the same zeroed
arrays.

## Equivalent BASIC

Unchanged — PB's guarantee that arrays and variables start zeroed is preserved,
just paid for at load time instead of on disk.

## Why it is safe

Only data whose initial content is **all zeros** is moved; anything with a
non-zero initializer (literals, `DATA` pools, pre-set tables) stays in the
image. The entry stub's zero-fill runs before any user code, so the first
observation of any BSS cell is already zero — the same order the loaded image
would have provided.
